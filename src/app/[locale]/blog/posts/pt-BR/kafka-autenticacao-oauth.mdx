# Introdução

No <a href={"/pt-BR/blog/kafka-ssl"}>post anterior</a> configuramos o Kafka com TLS, garantindo que os dados trafegam criptografados entre clientes e broker. Agora, qualquer tentativa de interceptar o tráfego encontra apenas ruído cifrado.

Mas isso resolve apenas metade do problema. TLS protege **o que** é transmitido, mas precisamos agora controlar **quem** pode se conectar. Com o setup atual, qualquer serviço que tenha acesso de rede ao broker consegue produzir mensagens, consumir dados e potencialmente injetar eventos maliciosos, mesmo sem conseguir ler o conteúdo de outras conexões.

Neste post vamos configurar **autenticação** no Kafka usando **SASL/OAUTHBEARER** com o <a href={"https://www.keycloak.org/"} target={"_blank"} rel={"noopener noreferrer"}>Keycloak</a> como servidor de autorização OAuth 2.0. Todo o código está disponível no <a href={"https://github.com/daanrsantiago/kafka-sasl-oauth-kotlin-example"} target={"_blank"} rel={"noopener noreferrer"}>repositório de exemplo</a> criado para acompanhar este post.

# Por que autenticação é importante no Kafka?

O Kafka funciona como um hub central de eventos em muitas arquiteturas de microsserviços. Mensagens de pedidos, transações financeiras, dados de usuários e logs de auditoria passam por ele o tempo todo. Sem autenticação, qualquer serviço com acesso à rede do broker pode:

- **Produzir eventos falsos** em qualquer tópico: um serviço comprometido pode injetar pedidos fraudulentos, acionar workflows indevidos ou corromper o estado de outros sistemas
- **Consumir dados sensíveis** de tópicos que não deveria acessar: um container com vulnerabilidade pode virar um ponto de exfiltração de dados
- **Fazer spoofing de producers**: enviar mensagens se passando por outro serviço, quebrando rastreabilidade e trilhas de auditoria

A defesa em profundidade que estamos construindo ao longo desta série tem três camadas: **criptografia** (TLS, que já configuramos), **autenticação** (quem você é, abordada neste post) e **autorização** (o que você pode fazer, no próximo post com ACLs).

# O que é OAuth 2.0?

OAuth 2.0 é um protocolo de autorização que permite que aplicações obtenham tokens de acesso de forma segura. No contexto do Kafka, usamos o **Client Credentials Flow**, um fluxo machine-to-machine sem usuário humano envolvido.

O fluxo funciona assim:

1. A aplicação (producer ou consumer) se autentica no servidor OAuth usando `client_id` e `client_secret`
2. O servidor OAuth retorna um **JWT** (JSON Web Token) assinado com sua chave privada
3. A aplicação apresenta esse JWT ao Kafka como prova de identidade

**JWT (JSON Web Token)**

Um JWT tem três partes separadas por ponto: `header.payload.signature`. O header indica o algoritmo de assinatura. O payload carrega as *claims*, que são informações como `iss` (quem emitiu), `aud` (para quem é destinado), `exp` (quando expira) e `sub` (o sujeito, a identidade da aplicação). A signature é calculada pelo servidor OAuth com sua chave privada, garantindo que ninguém adulterou o token.

**JWKS (JSON Web Key Set)**

Para validar a assinatura do JWT sem precisar consultar o servidor OAuth a cada mensagem, o broker Kafka busca as **chaves públicas** do servidor via um endpoint JWKS. Essas chaves ficam em cache: o broker valida cada token localmente, de forma offline. Isso é importante para a performance: a autenticação não adiciona uma chamada de rede extra por mensagem produzida ou consumida.

**Por que OAuth para o Kafka?**

Comparado a credenciais estáticas (usuário/senha com SASL/PLAIN ou SCRAM), o OAuth traz vantagens importantes:

- **Identidades centralizadas**: um único servidor de identidade para todos os serviços, e rotacionar credenciais de um serviço não exige reconfigurar o broker
- **Tokens com expiração curta**: se um token for capturado, ele expira automaticamente
- **Sem reinicialização do broker**: novas credenciais de clientes não exigem reconfiguração no broker
- **Integração com IAM corporativo**: Keycloak, Auth0, Okta. O Kafka vira mais um cliente do seu provedor de identidade existente

# Como funciona o SASL/OAUTHBEARER no Kafka

SASL (Simple Authentication and Security Layer) é um framework de autenticação usado pelo Kafka. OAUTHBEARER é o mecanismo SASL que usa JWTs como tokens bearer.

O fluxo completo tem três fases:

**Inicialização do broker:** ao subir, o broker busca as chaves públicas do Keycloak via endpoint JWKS e as mantém em cache. Toda validação de token que acontecer depois usará essas chaves localmente.

**Obtenção do token (Client Credentials Flow):** antes de conectar ao broker, o producer ou consumer chama o endpoint `/token` do Keycloak com `client_id` e `client_secret`. O Keycloak retorna um JWT assinado com `aud=kafka-broker` no payload, indicando que o token foi emitido especificamente para ser apresentado ao broker.

**Handshake SASL/OAUTHBEARER:** o cliente anuncia que quer usar OAUTHBEARER, o broker confirma, e então o cliente envia o JWT. O broker valida:

- **Assinatura**: usando a chave pública JWKS em cache, o que garante que o token não foi adulterado
- **`aud`**: deve conter `kafka-broker`, o que impede que tokens emitidos para outros serviços funcionem aqui
- **`iss`**: verifica que o token veio do issuer esperado e rejeita tokens de outros realms ou servidores
- **`exp`**: rejeita tokens expirados

Se todas as validações passarem, a conexão é estabelecida e o cliente pode produzir e consumir normalmente.

O Keycloak precisa estar configurado antes do broker, pois o broker vai buscar as chaves JWKS na inicialização. Suba-o primeiro:

## 2. Configurando o Keycloak

### 2.1 Criando o realm `kafka-example`

No menu superior esquerdo, clique em **Manage realms** → **Create realm**.

![Criar realm no Keycloak.](/images/posts/kafka-autenticacao-oauth/01-create-realm.png)

- **Realm name:** `kafka-example`
- Clique em **Create**

![Configuração do nome do realm.](/images/posts/kafka-autenticacao-oauth/02-realm-name.png)

### 2.2 Criando o client `kafka-broker`

Este client representa o próprio broker Kafka. Ele precisa de credenciais para autenticar suas conexões internas com o Keycloak e buscar tokens para uso interno.

No menu lateral, vá em **Clients** → **Create client**.

![Criar client no Keycloak.](/images/posts/kafka-autenticacao-oauth/03-create-client.png)

**Página 1 (General Settings):**
- **Client type:** OpenID Connect
- **Client ID:** `kafka-broker`
- Clique em **Next**

![Configurações gerais do kafka-broker.](/images/posts/kafka-autenticacao-oauth/04-kafka-broker-general.png)

**Página 2 (Capability config):**
- **Client authentication:** ON
- Desmarque **Standard flow**
- Marque **Service accounts roles**
- Clique em **Next** → **Save**

![Configuração de capabilities do kafka-broker.](/images/posts/kafka-autenticacao-oauth/05-kafka-broker-capability.png)

Após salvar, vá à aba **Credentials** e copie o **Client secret**, pois você vai precisar dele para configurar o `docker-compose.yaml`.

![Client secret do kafka-broker.](/images/posts/kafka-autenticacao-oauth/06-kafka-broker-secret.png)

### 2.3 Adicionando o audience mapper ao `kafka-broker`

O broker valida que todo JWT recebido contém `kafka-broker` no campo `aud`. Para isso, é necessário configurar um mapper que adicione essa claim aos tokens emitidos.

Vá em **Clients** → `kafka-broker` → aba **Client scopes** → clique no scope `kafka-broker-dedicated`.

![Client scope do kafka-broker.](/images/posts/kafka-autenticacao-oauth/07-kafka-broker-scope.png)

Na aba **Mappers** → **Configure a new mapper** → selecione **Audience**.

![Adicionar mapper — passo 1.](/images/posts/kafka-autenticacao-oauth/08-add-mapper-1.png)

![Adicionar mapper — passo 2.](/images/posts/kafka-autenticacao-oauth/08-add-mapper-2.png)

- **Name:** `kafka-broker-audience`
- **Included Custom Audience:** `kafka-broker`
- Clique em **Save**

![Configuração do audience mapper.](/images/posts/kafka-autenticacao-oauth/09-audience-mapper.png)

### 2.4 Criando o client `kafka-client`

Este client é usado pelas aplicações Kotlin, tanto o producer quanto o consumer. Repita os mesmos passos do **2.2**, com uma diferença:

- **Client ID:** `kafka-client`

Após salvar, copie o **Client secret** na aba **Credentials**.

![Client secret do kafka-client.](/images/posts/kafka-autenticacao-oauth/10-kafka-client-secret.png)

### 2.5 Adicionando o audience mapper ao `kafka-client`

Repita os mesmos passos do **2.3** para o client `kafka-client`:

**Clients** → `kafka-client` → **Client scopes** → `kafka-client-dedicated` → **Mappers** → **Configure a new mapper** → **Audience**

- **Name:** `kafka-broker-audience`
- **Included Custom Audience:** `kafka-broker`
- Clique em **Save**

![Audience mapper do kafka-client.](/images/posts/kafka-autenticacao-oauth/11-kafka-client-audience-mapper.png)

# Conclusão

Neste post adicionamos a segunda camada de segurança ao nosso cluster Kafka: autenticação com identidade verificável. O Keycloak atua como Authorization Server, emitindo JWTs assinados para as aplicações autorizadas. O broker valida cada token localmente usando as chaves JWKS em cache, sem chamadas de rede adicionais por mensagem. Clientes sem credenciais válidas simplesmente não conseguem se conectar.

Mas saber **quem** está conectado não é suficiente: precisamos controlar o que cada identidade pode fazer. Um producer autenticado não deveria conseguir consumir tópicos de outros domínios. Um consumer de relatórios não deveria ter permissão para produzir eventos de pagamento. No próximo post vamos configurar **autorização com ACLs no Kafka**, definindo políticas granulares de acesso por tópico e operação.
